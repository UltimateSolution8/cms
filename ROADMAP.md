# Roadmap

What has shipped, and what is still open with the check that closes it. The binding date is
**13 May 2027**, when the substantive DPDP Rules become enforceable; Denave is the pilot entity.

`PLAN` means `~/.claude/plans/we-want-to-build-staged-widget.md`, which carries each phase's delivery
record, defects found, and deviations with reasons. `DECISIONS.md` is the index of decisions.

## Open — the platform's side

Each item's acceptance criterion is a check somebody can run, not an aspiration.

| Item | Done when |
|---|---|
| **An IdP to point at** — **closed on the development half, open on Entra** | The criterion is met against a real OpenID Provider: `docs/WALKTHROUGH.md` §19 walks it with real output — a Keycloak token reaches `/v1/evaluate`, an `entity.MATRIX` app role reads `MATRIX` and is refused `DENAVE_IN` with 403, a token naming two entities is refused rather than resolved, and `admin_audit_event.actor_id` reads `denave.operator` from the token with **no `X-UDS-Actor` sent**. `KeycloakIssuerIT` pins it, asserting the entity at the **database session** rather than only at an HTTP status. The throughput half is settled too and it was not a small effect — `CAPACITY.md` §9: 43 rps under Basic against **153 rps** under Bearer at the same offered load, p95 5.58 s against **8.11 ms**. **What remains is Entra**, and none of it is a commit: `accessTokenAcceptedVersion: 2`, the exact `aud` string decoded from a real token, `preferred_username` as an optional claim, and who assigns `entity.<ID>`. `OPERATIONS.md` §2.3a is the checklist; `REGULATORY_HANDOFF.md` §8.8 is the decision |
| **An OTLP collector** | A span from a portal submission appears in the collector, and its `traceId` matches the one in the log line beside the caller's `correlationId`. The exporter key is now correct; nothing consumes it |
| **Encryption at rest** | The database volume and the WAL archive are both encrypted, and the archive lands in the residency region recorded on the entity — Rule 13(4) reaches the backup, not only the primary. Infrastructure layer; `RUNBOOK_DR.md` §6 |
| **A rehearsal on the group's hardware** | `RUNBOOK_DR.md` §4 walked on real infrastructure, timed, ending in a clean integrity sweep — then §2's RPO and RTO ratified or replaced. The laptop rehearsal measured the procedure, not the target |
| **A preference centre** | Deliberately not scheduled. It needs an authenticated session model for data principals; until then it would be an unauthenticated write path into the ledger. `DECISIONS.md`. **Phase 15 note: the field considers this table stakes** — three of five products torn down ship one, and the decision is worth re-litigating at the Phase 1 gate rather than treated as settled (`docs/competitive-analysis.md` §C.3) |
| **A Google Consent Mode v2 projection** | A GTM property's tags read GCM and cannot see `/v1/evaluate`, so a UDS website's consent decisions are invisible to Google's tags. Done when a decision projects to the seven GCM parameters — computed by the same `consent-core` engine, mapping held as registry data, never a second policy. **Per-subsidiary override is a build, not a reuse** — nothing in the purpose registry inherits today, and the criterion said otherwise for three phases on the strength of a false invariant (rules §3, Phase 16 closure C6). `docs/standards/tcf-and-consent-mode.md` §3–4 |
| **Notice translations, 19 of 23 languages** | `GET /v1/notices/reports/coverage` names the gap and correctly refuses placeholder rows. Done when it reports full coverage for the languages Rule 3 requires. Procurement, not code — and the one place a competitor's published claim beats the platform on a statutory obligation (§C.5) |
| **The 27560 Parties and Events remainder** | Recorded rather than half-built: typed party roles, postal addresses, enumerated rights, Consent Type, Expression by Entity. Each is a `partial` row in `docs/TRACEABILITY.md` §6 with the section it fails. **Consent Type is the cheapest** — `CaptureMethod` already encodes implied/expressed/explicit, so a derived accessor fills a mandatory field with no new data. None is an obligation under any clause the group is subject to |
| **The uncovered gauge is group-wide and untagged** | Deliberate, to bound cardinality — but the critical alert fires with no entity in it, and the responder's first step is to call a per-entity route fifteen times. Done when the alert carries enough to start on, without a label per fiduciary |
| **Disclosure is not linked to a rights request** | Phase 18 gates the *claim* of fulfilment on a recorded verification, and `GET /v1/admin/evidence/subject/{entityId}/{subjectId}` is unlinked from any `rights_request` — so an operator can still assemble and disclose a person's whole file without ever opening one, and the gate never sees it. Not closed in Phase 18 because the fix needs a rule for the legitimate uses of that route which are *not* a rights request — a breach investigation, an internal audit — and inventing one to satisfy a gate is policy written backwards. Done when a disclosure either carries a request reference or is recorded as deliberately not having one, and the audit row says which |
| **Verification cannot be corrected, only recorded** | `POST /v1/rights/{id}/verification` is write-once: a second call is refused 409 and the first record stands, because the row is evidence about what a named person did. An operator who records the wrong detail therefore has no route at all. Done when a correction is a **superseding record** — the `subject_alias` shape, where a merge is never a rewrite — rather than an edit, or when it is decided that no correction path is wanted and that is written down |
| **The divergences route discloses without an audit row** | `GET /v1/admin/evidence/subject/**` records `EVIDENCE_BUNDLE_ASSEMBLED` because it discloses one person's file; `GET /v1/admin/projection/divergences` now discloses subject ids, purposes and consent statuses for an entity and records nothing. Phase 20's own clause row cites Rule 6 access control, and *who read this* is half of that. Done when the route writes an audit event naming the actor, the entity and the count |
| **Three sweeper reports return unbounded group-wide id lists** | `POST /v1/admin/retention/sweep` returns `overdueActionIds`, `…/reconfirmation/sweep` returns `overdueIds`, and the breach SLA sweep returns `overdueObligations` — all gathered by a background job on a group-level session, so neither isolation layer is in the path, and all unbounded. Row ids rather than subject ids, which is a real difference in severity and none at all in the rule (rules §1). Found by Phase 20's audit and left, because the fix is the same shape as A1 and folding three more routes into a closing phase is how a scope grows. Done when each is entity-scoped or bounded the way the projection report now is |
| **Nothing enforces the sweeper-output isolation rule on the next route** | Layer two scopes the session that queries, so a route returning rows the request selected is covered even with no entity in its path, and one returning rows a **sweeper** gathered is not — the projection report was on the wrong side of that and was found by reading, not by a control. The rule is now in rules §1 and the admin surface was audited clean in Phase 20. Done when a test derives the set of routes returning a background job's output and asserts each is entity-scoped, the way `RowLevelSecurityIT` derives its protected tables from `information_schema` rather than listing them |
| ~~Nothing detects an OpenAPI schema-name collision~~ **closed, Phase 21** | `OpenApiContractIT.schemaNamesDoNotCollide` fails on any schema springdoc had to disambiguate, and `operationIdsAreStable` fails on an auto-numbered `_N` id — which caught a collision introduced by the fix for it, on its first run |
| **The reconciliation sweep's chain walk is unmeasured at population scale** | `CAPACITY.md` §8 measured it at 0.29 ms per subject against **502** real chains, because `perf/seed.sql` writes projections and no events — deliberately, and its header argues the case. So the artefact scan is measured and the dominant cost is extrapolated. Done when a fixture produces valid chains at volume — captures cost one BCrypt each (§7), so ~20,000 subjects is about seven minutes of load rather than something a test can do — and the sweep is timed against them |
| **Aggregates over RLS-protected tables plan against a fabricated estimate** | Found in `countWithoutChain`: the policy calls `current_setting()`, the planner cannot estimate it, assumes 0.5% selectivity and chooses a nested loop — 3,438 ms against 45 ms for a set-operation form, and unchanged by `ANALYZE` (`CAPACITY.md` §8.3). Fixed there; **not looked for anywhere else**. Every suite runs as the table owner, where no policy applies, so no test can see this class at all. Done when the other aggregates over `consent_event`, `enforcement_decision` and `consent_artefact` have been explained as `uds_consent_app` and either cleared or rewritten |
| **§3.3a step 3 is still unrehearsed** | Steps 1 and 2 were walked on 19 August 2026 (`WALKTHROUGH.md` §18). Step 3 — re-project the affected chains — was not, deliberately: there is no route that does it, so it is a person with database access making a decision under incident pressure, and a laptop rehearsal against a fabricated subject would prove nothing. Done when it is walked on real infrastructure with a named owner, the way `RUNBOOK_DR.md` §5 was |
| **Gate 11a's replay direction is pinned, not resolved** | It reads the artefact's `captureMethod` as it stands now, where gate 7 asks minority as at the decision instant, so a decision replayed before a later guardian-verified re-capture allows. `GuardianVerificationIT.aReplayedDecisionReadsTodaysCaptureMethod` names the behaviour so that changing it is a decision rather than an accident. Done when UDS's counsel has said whether a replayed child decision must answer as at the day — the fix is a chain walk on the decision path, which `CAPACITY.md` §7 costs at more than the whole decision budget |
| **`dpv-pd` against the 17 `data_category` codes** | Personal Data Type is mandatory in the record structure and the platform's codes are locally invented, so that axis is unmapped rather than mapped-and-clean. Done when each code carries a `broader` pointer to its nearest DPV term. `docs/standards/dpv-v2-vocabulary.md` §6 |

| **Group level is what silence means, and it should be an explicit opt-in** | A credential with no `entity_id` claim, no `entity.<ID>` role and no configured `entity-id` is group level — it reads every fiduciary in the group through both isolation layers. That is one rule for both authentication schemes, which is why it has survived; it also means an issuer that simply forgot the claim produces the widest possible grant and nothing looks wrong. Fail-closing only the entity-bearing routes was considered in Phase 21 and rejected as theatre: the dangerous routes are the ones with no entity in path or query that still return entity-scoped rows through RLS — `/v1/rights/queue`, `/overdue`, `/summary`, most of `/v1/admin/**`. Done when group level is something a credential *claims* rather than something it omits — a `group-level: true` flag on a client and an equivalent explicit token value, applied to **both** schemes or neither, with start-up refusing a credential that has neither. A build, not a tweak |
| **The isolation control has moved partly into the identity provider** | Which entity a caller may see is now an app-role or claim assignment in Entra or Keycloak that no test here can execute and no document under `docs/` describes. `RowLevelSecurityIT` keeps passing while the assignment is wrong. Done when `OPERATIONS.md` §8's checklist carries the command that decodes a real token and shows the claim, and `REGULATORY_HANDOFF.md` §8 records who assigns the entity role and to whom |
| **A browser client is a trust boundary nothing describes** | `OPERATIONS.md` §12 describes the front door for machine callers. Nobody has written down token lifetime, refresh handling, or what an XSS in a console holding an ADMIN token reaches — which, per rules §6, includes the evidence bundle with no rights request opened. Done when §12 has a subsection for browser clients, written before one is deployed rather than after |
| **The pre-auth bucket now serves a browser population** | 400/s per address was sized for machine callers behind a NAT and measured only for machine traffic (`CAPACITY.md` §7). A hundred console users behind one corporate egress is a different shape against the same single bucket. Preflights no longer count against it, which helps. Done when the console's traffic profile is measured rather than assumed |
| **The audit trail records an opaque `sub` under Entra** | `Actor` reads `preferred_username`, then `email`, then `sub`. Entra does not put `preferred_username` in an access token for a custom API without an optional claim on the resource registration — so the first admin mutation from a console writes a pairwise identifier, meaningless outside the directory, permanently into an append-only table. Done when the optional claims are configured, a real token is decoded to prove it, and the fallback to `sub` logs at WARN |

| **Set `dpo_contact` and `grievance_uri` on the `UDS` row** | Every receipt names a null DPO contact, against DPDP Rule 3 | `EntityContactCheck` is silent at start-up. One statement fixes all fifteen entities |

| **Build a consumer for `rights.verification.requested`** | Every portal submission expires unverified, so Rule 14(1)'s published URL would be a dead end | A verification message reaches a real contact and the token verifies. Small integration, hard prerequisite |
| **Decide the identifier list Rule 14(1) requires published** | The portal accepts any single identifier because no list exists to check against | The list is published and enforced at intake |
| **Register the systems that must receive a withdrawal** | **Phase 17 built the register; UDS populates it.** `propagation_target` now names who must be told, and a mandatory target nothing can reach is reported as uncovered rather than leaving no trace — but no entity has one configured, so the gauge reads zero and the instruments are indistinguishable from full coverage. The same shape as `fulfilment_target`, and it needs the §8.7 signature rather than a commit | **Every mandatory `propagation_target` resolves to an active subscription and `uds_consent_propagation_uncovered` reads zero**, and a withdrawal produces a `webhook_delivery` row against each. The old criterion — *"at least one active subscription exists"* — was unfalsifiable from inside the platform: nothing said how many there should be. `REGULATORY_HANDOFF.md` §8.7 is the register UDS signs. *`docs/TRACEABILITY.md` §3* |
| **Decide what happens to the children's-gate denials** | Phase 19 refuses a decision for a subject who is a child when the consent relied on records no verified guardian (s.9(1) + Rule 10, at processing rather than only at capture). Every existing consent for a subject later asserted a minor now refuses. The platform does not know how many | The per-entity count is run against `subject_age_assertion` **before** the change reaches production, a re-consent path from a verified guardian has an owner, and UDS's counsel has confirmed or replaced the narrow reading — the gate applies to consent-based decisions only, so s.7(i) employment processing of an under-eighteen is not checked. *`REGULATORY_HANDOFF.md` §8.6a* |
| **Say what `OPERATOR_ASSERTED` must mean before a console offers it** | The field is free text and the platform cannot check it | A one-paragraph standard — a call-back to a number already on file, an employee ID checked at a desk, a document reference — published to the compliance team, and the share of open requests reading `UNVERIFIED` watched rather than merely queryable. The platform records the claim; what makes a claim adequate is UDS's to state. *`docs/TRACEABILITY.md` §1, Rule 14(3) admin-intake row* |
| **Create the production database in an Indian region** | The Supabase project provisioned in Phase 22 is in **`ap-southeast-1` (Singapore)**, resolved from the host's IPv6 address against AWS's published ranges rather than read off a label. `OPERATIONS.md` §1.2 requires the DPDP-scoped ledger in India and `V3` seeds `DENAVE_IN` with `residency_region = 'ap-south-1'`, so the platform's own record already disagrees with where it is running. Fine for development against fabricated data; it is not a production database for Indian personal data | A project exists in an Indian region, `deploy/hosted/provision.sql` and `verify.sql` both pass against it, and §1.2's residency statement names it. **A region cannot be changed after a project is created**, so this is a new project rather than a migration — and the development one stays development. Rotating the credential that arrived in a chat message belongs here too |
| **Decide who assigns the `entity.<ID>` app role, and to whom** | Pointing the platform at an identity provider moves half the isolation control out of this repository. Which fiduciary a caller may act for can now be a directory assignment that no test here executes, no document under `docs/` describes, and `RowLevelSecurityIT` passes regardless of. The platform's half is done — one resolver feeds both layers, two entity roles are refused, and the resolved value is asserted at the database session | A named owner for the assignment, a written rule for who may hold which entity role, and a periodic review with a date. Note the standing default: **a credential carrying neither claim nor role is group level**, so an issuer that simply forgot produces total access and nothing looks wrong. *`REGULATORY_HANDOFF.md` §8.8* |
| **Decide private-key custody** | The public side of rotation is survivable; the private half is still an environment variable | A `SigningKeyProvider` backed by the group's KMS is the configured bean. Now a swap, not a refactor |

## Working the roadmap

`/next-phase` is the entry point: re-read `DECISIONS.md` and `docs/standards/` directly, confirm the
previous phase against the criteria above and **flag gaps rather than carrying them**, then plan with
clause citations and wait for approval. `/phase-gate` closes a phase; nothing is committed without an
explicit instruction.
