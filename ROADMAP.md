# Roadmap

What has shipped, and what is still open with the check that closes it. The binding date is
**13 May 2027**, when the substantive DPDP Rules become enforceable; Denave is the pilot entity.

`PLAN` means `~/.claude/plans/we-want-to-build-staged-widget.md`, which carries each phase's delivery
record, defects found, and deviations with reasons. `DECISIONS.md` is the index of decisions.

## Open — the platform's side

Each item's acceptance criterion is a check somebody can run, not an aspiration.

| Item | Done when |
|---|---|
| **An IdP to point at** | A token from the group's provider reaches `/v1/evaluate`, its `entity_id` claim scopes it to one entity (proven by a second entity's record returning 403), and `admin_audit_event.actor_id` carries a human from the token with no `X-UDS-Actor` sent. This is also the throughput ceiling: JWT does not re-hash a credential per request |
| **An OTLP collector** | A span from a portal submission appears in the collector, and its `traceId` matches the one in the log line beside the caller's `correlationId`. The exporter key is now correct; nothing consumes it |
| **Encryption at rest** | The database volume and the WAL archive are both encrypted, and the archive lands in the residency region recorded on the entity — Rule 13(4) reaches the backup, not only the primary. Infrastructure layer; `RUNBOOK_DR.md` §6 |
| **A rehearsal on the group's hardware** | `RUNBOOK_DR.md` §4 walked on real infrastructure, timed, ending in a clean integrity sweep — then §2's RPO and RTO ratified or replaced. The laptop rehearsal measured the procedure, not the target |
| **A preference centre** | Deliberately not scheduled. It needs an authenticated session model for data principals; until then it would be an unauthenticated write path into the ledger. `DECISIONS.md`. **Phase 15 note: the field considers this table stakes** — three of five products torn down ship one, and the decision is worth re-litigating at the Phase 1 gate rather than treated as settled (`docs/competitive-analysis.md` §C.3) |
| **A Google Consent Mode v2 projection** | A GTM property's tags read GCM and cannot see `/v1/evaluate`, so a UDS website's consent decisions are invisible to Google's tags. Done when a decision projects to the seven GCM parameters — computed by the same `consent-core` engine, mapping held as registry data, never a second policy. **Per-subsidiary override is a build, not a reuse** — nothing in the purpose registry inherits today, and the criterion said otherwise for three phases on the strength of a false invariant (rules §3, Phase 16 closure C6). `docs/standards/tcf-and-consent-mode.md` §3–4 |
| **Notice translations, 19 of 23 languages** | `GET /v1/notices/reports/coverage` names the gap and correctly refuses placeholder rows. Done when it reports full coverage for the languages Rule 3 requires. Procurement, not code — and the one place a competitor's published claim beats the platform on a statutory obligation (§C.5) |
| **The 27560 Parties and Events remainder** | Recorded rather than half-built: typed party roles, postal addresses, enumerated rights, Consent Type, Expression by Entity. Each is a `partial` row in `docs/TRACEABILITY.md` §6 with the section it fails. **Consent Type is the cheapest** — `CaptureMethod` already encodes implied/expressed/explicit, so a derived accessor fills a mandatory field with no new data. None is an obligation under any clause the group is subject to |
| **The propagation admin routes have no integration test** | `GET`/`PUT /v1/admin/propagation/targets` and `GET /gaps` are exercised only by `OpenApiContractIT`, which proves the mappings render and nothing else. Untested: the `hasRole('ADMIN')` boundary, the `PROPAGATION_TARGET_CONFIGURED` audit row, the `X-UDS-Actor` requirement under Basic, and the resolved-subscription-per-target field that is the operator's only view of a `system_code` mismatch. Done when each is asserted over HTTP through `IntegrationTestClient` |
| **`propagation_gap` is not in `LedgerAppendOnlyIT`'s list** | The suite's hand-written list covers three tables; `webhook_delivery` and `rights_fulfilment_action` were already outside it, and Phase 17 added a fourth evidence table without extending it. The revoke is in `V31` and nothing proves it holds **as `uds_consent_app`**, which is the only role whose refusal means anything. Done when all four are covered, or the list is derived the way `RowLevelSecurityIT`'s is |
| **`system_code` has no controlled vocabulary, so a typo writes permanent false evidence** | The propagation register joins `propagation_target.system_code` to `webhook_subscription.system_code` as free text, upper-cased on both sides. A target for `DENCRM` against a subscription called `DENCRM_PROD` produces a phantom gap indistinguishable from a real one — and `propagation_gap` is append-only, so those rows are permanent evidence of a failure that never happened. `fulfilment_target` gets the same class of error right by failing loud and closed (409 naming the system); here it fails quiet. Done when a mismatch is refused at `PUT` time against a registered vocabulary, or the register is keyed to something the database can enforce |
| **Nothing warns that propagation is unobservable under the shipped publisher** | `webhook_delivery` is written only by the webhook publisher; the default is `log`, which is what the pilot runs. So every gap reads `NO_DELIVERY_CHANNEL` — honest, and not evidence. The instruments look identical to full coverage. Done when a start-up check or an alert names the condition "targets are registered and the publisher cannot evidence delivery", the way `PropagationTopicCheck` names an unpublished topic |
| **A downstream system that is *down* produces no gap row** | A failing endpoint leaves the message unpublished and the relay breaks, so the reconciler never runs for it. Configuration errors land in `propagation_gap`; unavailability lands in `webhook_delivery` `FAILED` rows and the ten-attempt escalation. Documented in `OPERATIONS.md` §4.0a, joined by nothing. Done when one read answers "is this system current?" across both, or the runbook says what to do when they disagree |
| **The uncovered gauge is group-wide and untagged** | Deliberate, to bound cardinality — but the critical alert fires with no entity in it, and the responder's first step is to call a per-entity route fifteen times. Done when the alert carries enough to start on, without a label per fiduciary |
| **`NOTICE_SERVED` erases an existing grant** | `POST /v1/consent/notice-served` (live, `ROLE_CAPTURE`, any `purposeCode`) writes an event resolving to `NOT_ASKED`. The projector does not stop it — `supersedes` compares time only, and `isAmbiguous` is false once the 5-minute skew window has passed — so re-serving a notice for a purpose the person already granted wipes the grant from `consent_artefact`, which is what `PolicyEngine` reads. Found while fixing the Phase 16 closure's own regression. Done when a `NOTICE_SERVED` behind an existing artefact either updates the notice fields alone or is ignored as stale — **a decision, not a patch**, and the s.7(i) workforce path is the one it must not break |
| **`purpose_version = 0` on `EXPIRED` and `INVALIDATED`** | `ExpirySweeper` and `ConsentCaptureService.invalidate` write `0` into the append-only table and onto the outbox payload. It is a sentinel for *no version asserted*, not a false claim — which is why the projection correctly carries the prior version forward — but it is untyped and undocumented, and a reader has no way to tell it from a real version. Done when it is either a nullable column or a named constant, documented either way |
| **Guardian evidence at decision time** | `PolicyEngine` gate 7 denies a child subject only on `!purpose.permittedForChildren()`. Capture refuses an unevidenced parental consent, so the live hole is a subject whose minority is established *after* capture, on a purpose that **is** permitted for children — allowed today on a consent nobody verified a guardian for. Done when that case denies, with a reason naming the missing evidence, and a test that fails without the gate |
| **Reconcile the projection against the chain** | `IntegritySweeper` verifies `consent_event` and nothing verifies `consent_artefact` against it, so an edited projection is invisible: `last_event_hash` is *copied* onto the artefact rather than derived from its `status`, and stays perfectly consistent. Done when a sweep re-projects and reports any artefact disagreeing with the status its chain implies. **Off the request path** — recomputing a chain per decision is unaffordable against a 2.6 ms p95 at ~50 rps, and would not detect this anyway |
| **Alert on sweeper staleness** | Thirteen rules in `alerts.yaml`, and only `PartitionRunwayShort` would notice a sweep having stopped — for one job. A silently dead `ExpirySweeper` writes no `EXPIRED` events and the evidence plane goes quietly incomplete while every decision stays correct, which is what makes it hard to spot. Done when each sweep publishes a last-run-age gauge and one rule watches them |
| **`for update skip locked` on the outbox relay** | `OutboxStore.fetchUnpublished` takes no lock and `OutboxRelay` — unlike all seven sweepers — takes no `SweepLock`, while `deployment.yaml` ships `replicas: 3`. Three relays drain the same batch every two seconds, so subscribers receive each event up to 3× and `webhook_delivery` carries up to three rows per attempt. Done in **its own change with its own test**; deliberately not folded into Phase 17, which would have serialised fan-out onto one instance as a side effect |
| **`dpv-pd` against the 17 `data_category` codes** | Personal Data Type is mandatory in the record structure and the platform's codes are locally invented, so that axis is unmapped rather than mapped-and-clean. Done when each code carries a `broader` pointer to its nearest DPV term. `docs/standards/dpv-v2-vocabulary.md` §6 |

## Open — UDS's side, which no commit can close

| Decision | Blocks | Done when |
|---|---|---|
| **Sign the rights-fulfilment scope statement and populate `fulfilment_target`** | `FULFILLED` can still be asserted with nothing behind it | The statement is signed and at least one mandatory target exists per entity and request type. *`REGULATORY_HANDOFF.md` §8.5* |
| **Set `dpo_contact` and `grievance_uri` on the `UDS` row** | Every receipt names a null DPO contact, against DPDP Rule 3 | `EntityContactCheck` is silent at start-up. One statement fixes all fifteen entities |
| **Decide how Denave keys a contact** across DenCRM, the HRMS and BGV | Identity resolution ships the mechanism with a safe default; the keying policy is theirs | `uds.consent.identity.strategy` set deliberately, and the rule written down. *§8.1* |
| **Build a consumer for `rights.verification.requested`** | Every portal submission expires unverified, so Rule 14(1)'s published URL would be a dead end | A verification message reaches a real contact and the token verifies. Small integration, hard prerequisite |
| **Decide the identifier list Rule 14(1) requires published** | The portal accepts any single identifier because no list exists to check against | The list is published and enforced at intake |
| **Register the systems that must receive a withdrawal** | **Phase 17 built the register; UDS populates it.** `propagation_target` now names who must be told, and a mandatory target nothing can reach is reported as uncovered rather than leaving no trace — but no entity has one configured, so the gauge reads zero and the instruments are indistinguishable from full coverage. The same shape as `fulfilment_target`, and it needs the §8.7 signature rather than a commit | **Every mandatory `propagation_target` resolves to an active subscription and `uds_consent_propagation_uncovered` reads zero**, and a withdrawal produces a `webhook_delivery` row against each. The old criterion — *"at least one active subscription exists"* — was unfalsifiable from inside the platform: nothing said how many there should be. `REGULATORY_HANDOFF.md` §8.7 is the register UDS signs. *`docs/TRACEABILITY.md` §3* |
| **Say what `OPERATOR_ASSERTED` must mean before a console offers it** | The field is free text and the platform cannot check it | A one-paragraph standard — a call-back to a number already on file, an employee ID checked at a desk, a document reference — published to the compliance team, and the share of open requests reading `UNVERIFIED` watched rather than merely queryable. The platform records the claim; what makes a claim adequate is UDS's to state. *`docs/TRACEABILITY.md` §1, Rule 14(3) admin-intake row* |
| **Decide private-key custody** | The public side of rotation is survivable; the private half is still an environment variable | A `SigningKeyProvider` backed by the group's KMS is the configured bean. Now a swap, not a refactor |

## Working the roadmap

`/next-phase` is the entry point: re-read `DECISIONS.md` and `docs/standards/` directly, confirm the
previous phase against the criteria above and **flag gaps rather than carrying them**, then plan with
clause citations and wait for approval. `/phase-gate` closes a phase; nothing is committed without an
explicit instruction.
